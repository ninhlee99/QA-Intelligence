# Purpose

Define the canonical vocabulary used throughout QA Intelligence.

Every Engineering Specification, AI Agent, Schema, API, Plugin and Knowledge Object MUST use the terminology defined in this document.

No module may redefine an existing term.

This document serves as the Domain Language of QA Intelligence.

---

# Background

Large software systems become inconsistent when different modules use different terminology.

Examples

Requirement

Specification

Feature

Capability

Scenario

Flow

Sometimes these words refer to the same concept.

Sometimes they do not.

QA Intelligence eliminates ambiguity by defining one canonical language.

---

Define

- domain terminology

- AI vocabulary
- testing vocabulary

- storage vocabulary

# Canonical Terminology

---

## AI

An intelligent reasoning component capable of understanding, analyzing and generating engineering outputs.

AI never owns business knowledge.

---

## Agent

A specialized reasoning module responsible for one engineering capability.

Examples

- Discovery Agent
- Requirement Agent
- Testing Agent

Every Agent owns exactly one responsibility.

---

## Engineering Specification

A formal document describing one engineering module.

Engineering Specifications are the highest implementation authority.

---

## Engineering Law

A mandatory engineering constraint.

Engineering Laws cannot be overridden.

---

## Product Principle

A product philosophy.

Product Principles guide engineering decisions.

---

## Governance

Rules defining AI authority and limitations.

---

## Discovery

The automated process of collecting information about an application.

Discovery includes

- UI

- API

- Route

- Permission

- Technology

- DOM

Discovery never generates testcases.

---

## Requirement

A statement describing expected system behavior.

Requirements are inputs.

They are not implementation.

---

## Business Rule

A validated rule describing business behavior.

Examples

Password expires after 90 days.

Email must be unique.

Business Rules generate validations.

---

## Validation

A constraint applied to data or workflow.

Validation originates from Business Rules.

---

## Knowledge

Validated engineering information.

Knowledge is structured.

Knowledge is reusable.

Knowledge is versioned.

Knowledge is never conversational.

---

## Knowledge Object

The smallest reusable knowledge unit.

Example

Business Rule

API Contract

Workflow

Permission

Validation

Locator

Risk

Every Knowledge Object owns

- ID

- Version

- Source

- Confidence

- Status

---

## Knowledge Candidate

Information waiting for validation.

Knowledge Candidates are temporary.

They never become project knowledge until validated.

---

## Knowledge Store

Persistent storage of validated Knowledge Objects.

Single Source of Truth.

---

## Memory

Runtime retrieval mechanism used to load relevant Knowledge Objects.

Memory is not knowledge.

Memory is a retrieval layer.

---

## Rule Engine

Deterministic engine responsible for evaluating engineering rules.

Rule Engine executes before AI reasoning.

---

## Evidence

Information supporting an engineering decision.

Examples

Requirement

Business Rule

API Response

Discovery Result

Execution Result

---

## Confidence

A measurable probability representing decision reliability.

Confidence never replaces evidence.

---

## Observation

Raw information collected during execution.

Observation is not knowledge.

---

## Validation Process

Engineering workflow verifying Knowledge Candidates.

Only validated information becomes knowledge.

---

## Semantic UI

A structured representation of user interface elements.

Semantic UI describes meaning.

It never stores raw HTML.

---

## UI Knowledge Graph

A graph describing relationships between UI components.

Examples

Page

↓

Section

↓

Control

↓

Validation

↓

Business Rule

---

## Traceability

Ability to trace every engineering artifact back to its origin.

---

## Artifact

Any output generated by QA Intelligence.

Examples

Testcase

Automation

Bug Report

Knowledge Object

Risk Analysis

Report

---

## Workspace

Project storage containing

Configuration

Knowledge

Reports

Automation

History

Artifacts

---

## Project

One isolated QA Intelligence working environment.

Projects never share Project Knowledge.

---

## Global Knowledge

Reusable knowledge shared across projects.

Example

Boundary Testing

OWASP

Accessibility Rules

---

## Project Knowledge

Knowledge unique to one project.

Example

Login Policy

Business Workflow

Permission Matrix

---

## Testing Strategy

High-level testing approach.

Generated after Requirement Analysis.

Before Testcase Generation.

---

## Testcase

One executable verification scenario.

Generated from

Business Rules

Requirements

Risk

Knowledge

---

## Automation

Executable test implementation.

Automation is generated after Testcases.

Automation never defines business rules.

---

## Execution

Running automated or manual tests.

Execution produces observations.

---

## Bug

A verified deviation between expected behavior and actual behavior.

---

## Report

Structured engineering output describing execution results.

---

## Learning

Controlled improvement of Knowledge Store through validated observations.

---

## Plugin

Integration layer connecting QA Intelligence with external IDEs.

Examples

Cursor

Claude Code

Codex

VS Code

Plugins never contain business knowledge.

---

## Core Engine

Central runtime responsible for coordinating all modules.

Core Engine owns orchestration.

---

## Orchestrator

Component responsible for coordinating Agents.

The Orchestrator never performs specialized work.
